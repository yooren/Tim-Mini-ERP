# Tim Mini ERP 开发记录

> 本文档记录项目从初版到当前版本的开发历程，按时间顺序整理，供团队内部追溯"为什么会是现在这个样子"。
> 客户侧的功能说明请看 [产品介绍](../产品介绍.md)，部署与配置操作请看 [部署与配置指南](部署与配置指南.md)。

## 阶段一：项目起步（2026-08-19）

**提交：`c56728f` Initial commit**

一次性搭建起系统的完整雏形：纯前端 HTML/CSS/原生 JavaScript，零构建、零依赖，双击即可运行；数据默认存在浏览器 localStorage。首个版本就覆盖了 30+ 业务模块——仓储（商品、入库、出库、盘点、调拨）、供应链（供应商、客户、采购、承运商）、生产（生产计划、BOM、委外、MES）、质量（IQC/IPQC/OQC、SPC、NCR）、设备台账、人力资源、销售 CRM、财务、物流运输，以及权限、账套、打印、审计日志等系统模块。同时给出了一个可选的 Node.js 后端雏形（`server/`，基于 `db.js`），为后续"多端共享数据"留出了扩展空间。

## 阶段二：数据库能力与授权体系（2026-09-02）

这一天集中做了五次提交，把系统从"能跑起来"补齐到"能真正卖给客户长期使用"：

- **`71bdffc` 新增可选 MySQL 数据库后端支持** —— 后端数据访问层拆分出 `db-sqlite.js` 独立实现，新增 `db-mysql.js`，两者接口保持一致；同时新增 `server/static-server.js`，解决"用 `file://` 直接打开前端页面时无法正常发起后端请求"的问题。
- **`3a05ce9` 品牌升级为综合业务管理系统 v3.0.0，新增授权期限管理与试用机制** —— 新增 `js/license.js`，系统开始具备授权码校验、试用期限管理的能力，为后续商业化分发打基础。
- **`5708a8b` 完善部署指南目录** —— 补全部署文档中指向 MySQL 配置教程的目录索引，方便非技术人员按图索骥完成配置。
- **`fcee297` 新增后台一键配置数据库功能** —— 在「系统设置」里新增 `server/env-config.js` 支持的一键配置数据库入口，客户不用再手改 `server/.env` 文件、不用重启服务器再手动排查，大幅降低了 MySQL 切换门槛。
- **`6ac41eb` 正式授权码支持限制最大并发在线用户数** —— 授权码体系进一步完善，正式授权可按需限制最大并发在线用户数（试用期不受限），为按规模分级授权的商业模式做好了技术准备。

## 阶段三：品牌重塑与全业务链条复盘（2026-09-08）

**提交：`db892ad` 品牌重塑为 Tim Mini ERP v1.0.0，并修复全业务链条复盘中发现的22个逻辑缺陷**

系统正式更名为 **Tim Mini ERP**，统一品牌视觉（Logo、登录页、单据打印、`产品介绍.md`/`产品介绍.pdf`），版本号归零重新定为 v1.0.0。这次提交的重点不是加新功能，而是一次对全业务链条的系统性复盘和修复，主要修复了：

- **权限矩阵默认放行漏洞**：此前权限未配置时默认允许操作，新账套/新角色也从不写入默认权限，导致低权限角色事实上拥有全部权限；改为默认拒绝，并在账套初始化时自动写入安全默认矩阵。
- **库存数据一致性问题**：仓库调拨在库存不足时仍会静默放行、凭空增加库存；入库/出库单编辑与删除时存在参数错误导致的静默不生效问题。
- **操作级权限校验大范围缺失**：除仓库调拨/管理模块外，其余 27 个业务模块的新建/编辑/删除/审核等操作完全没有接入权限校验（配置了权限矩阵也不生效）；补齐了全部业务模块 200+ 处操作的校验。
- **账套切换会清空数据的严重缺陷**：此前切换账套会清除"已初始化"标记，导致再次进入时被示例数据整体覆盖，表现为"数据无故消失"；修复为只在账套首次使用时初始化。
- **默认账套/新建账套的示例数据混淆**：内置账套明确标注为"演示账套"，管理员新建的账套不再自动带入示例数据。
- **服务端数据库支持独立 MySQL**：`server.js` 统一改为 `async/await`，配合前面阶段拆分的 `db-sqlite.js`/`db-mysql.js`，通过 `.env` 的 `DB_TYPE` 即可切换，无需改代码。

**提交：`12c2e5b` 补上三处此前标记为"需产品决策"的功能缺口**

在复盘过程中发现三处此前被标记为"需要产品决策后再实现"的功能缺口（涉及 CRM、库存盘点、MES、打印模块），此次逐一做出产品判断并补全了具体实现。

## 阶段四：细节修复与本地升级包机制（2026-09-10）

**提交：`e25af9f` 修复登录页账套选择框文字被图标遮挡重叠的问题**

登录页的账套选择下拉框（`<select>`）左侧文字与账套图标重叠——根因是该下拉框沿用了普通输入框的内边距，但图标定位方式与 `<input>` 不同，`<select>` 没有吃到留白规则。修复方式是单独为该下拉框补上左侧留白。

**提交：`afa8a3b` 新增本地升级包机制，支持离线上传升级包完成版本升级与一键回滚**

这是本轮开发中投入最大的一个功能：**版本升级机制**。设计上直接参照传统进销存软件（管家婆、速达等）的做法——厂商把新版本打成一个 zip 升级包，客户在系统里自己上传即可完成升级，**不依赖联网检查更新**，这对很多部署在客户内网、平时不联网的环境尤其重要。

技术实现要点：

- 新增 `server/upgrade.js`：解压升级包（`adm-zip`）、校验 `version.json`、逐项覆盖 `web-src/`（`TimMiniERP.html`/`LOGO.svg`/`css/`/`js/`/`docs/`）与 `server-src/`（`server/` 下的 `*.js` 文件），升级前自动把即将被替换的文件备份到 `server/data/upgrade-backups/<时间戳>/`，支持一键回滚。
- **安全边界**：显式的 `FORBIDDEN_WEB_ENTRIES`/`FORBIDDEN_SERVER_ENTRIES` 名单，确保升级包内容无论如何都碰不到 `server/`、`node_modules/`、`data/`（账套数据库）、`.env`（连接配置）；解压时做 zip-slip 路径穿越检查，防止恶意或手滑的升级包通过 `../` 之类路径跳出预期目录。
- **不做自动重启**：应用完升级包后需要管理员手动重启一次后端服务才会生效。这是有意的设计选择——Node 进程在没有守护进程（pm2/systemd 等）看管时自己重启自己并不可靠，一旦升级包里代码有问题，自动重启可能导致服务彻底起不来且无人知晓。
- 新增 `js/pages/settings.js` 里「系统设置 → 系统信息 → 版本升级」的完整交互界面：当前版本展示、升级包上传、应用前二次确认、升级历史列表、按历史记录一键回滚。
- 新增仅供厂商内部使用、不随产品分发的打包工具 `tools/build-upgrade-package.js`（`tools/` 目录已在 `.gitignore` 中排除），打包前会对所有 `.js` 文件跑一次 `node --check` 语法体检，避免把有问题的代码打进升级包发给客户。

开发中修复的几个问题：

- 路由注册顺序问题：新增的 `GET /api/admin/upgrade-status` 一开始注册在通用的 `/api/:accountId/:collection` 路由之后，被后者提前捕获、误判成"账套 admin 不存在"；调整注册顺序后修复。
- 临时目录清理：升级包校验失败（如缺少 `version.json`、zip-slip 攻击被拦截）时，原逻辑会跳过临时解压目录的清理，导致每次失败尝试都留一份垃圾数据；改为 `try/finally` 保证无论成功失败都清理。
- 依赖版本：`multer` 从存在已知漏洞的 1.x 升级到 2.x。

功能完成后做了两轮验证：一轮在隔离的临时测试环境里用 curl + 真实浏览器走完整流程（应用、回滚、拒绝无效升级包、拦截路径穿越攻击、临时目录清理）；另一轮直接在真实项目环境里打包了一个 `v1.0.1` 测试升级包，完整走了一次"上传 → 应用 → 版本号变化 → 出现在升级历史 → 回滚 → 版本号恢复"的真实流程，确认功能可用后清理了测试数据，正式版本保持在 v1.0.0。

同时把这次调整同步到了已发布的 GitHub Release（v1.0.0）安装包里：下载现有的 Windows/Linux 免安装包，直接在原始压缩包基础上补入新增文件与依赖（避免了解压重新打包过程中中文文件名编码错乱、Linux 可执行权限丢失等坑），并用打包内置的 Node 运行时实际启动验证后重新上传。

## 待办 / 后续方向

以下是目前已知但尚未处理的事项，供后续排期参考：

- `tools/build-upgrade-package.js` 目前依赖手动执行；后续如果发布频率变高，可以考虑接入 CI 自动打包。
- 版本升级机制目前只覆盖代码文件，`server-package.json` 里的依赖变化只做检测提示，不会自动 `npm install`——如果某次升级引入了新依赖，还是需要人工介入安装。
- 项目根目录已更名为 `Tim Mini ERP`（原目录名"智能业务管理系统"是历史遗留），后续新建的本地路径、文档、脚本注意保持这个命名。
