## 1. 系统概述

Tim Mini ERP 是一款一体化企业业务管理系统（ERP），仓储管理（WMS）只是其中一个子系统，实际覆盖生产制造、质量管控、设备、人力资源、销售CRM、财务、物流运输等全业务链条。系统默认以纯前端形式运行（数据存于浏览器 localStorage），也可选配 `server/` 目录下的 Node.js 后端数据库实现多端数据共享，涵盖以下核心模块：

| 模块分类 | 功能模块 |
|---------|---------|
| 仓储核心 | 商品管理、入库管理、出库管理、库存盘点、仓库调拨 |
| 供应链 | 供应商管理、客户管理、采购管理、承运商管理 |
| 生产制造 | 生产计划、BOM管理、委外加工、MES |
| 质量管控 | IQC来料检、IPQC过程检、OQC出货检、SPC |
| 设备管理 | 设备台账、维护保养、EAM |
| 人力资源 | 部门管理、员工管理、考勤管理 |
| 销售CRM | 销售线索、报价、订单、KPI、会员管理 |
| 财务 | 发票管理、财务记录 |
| 物流运输 | 运输计划、配送单、运费管理 |
| 系统管理 | 用户/角色/权限、账套管理、打印设置、审计日志 |

## 2. 环境要求

### 2.1 客户端要求

| 项目 | 最低要求 | 推荐配置 |
|-----|---------|---------|
| 浏览器 | Chrome 90+ / Edge 90+ | Chrome 最新版 |
| 分辨率 | 1366×768 | 1920×1080 及以上 |
| JavaScript | 必须启用 | - |
| localStorage | ≥ 5MB 可用空间 | ≥ 10MB |
| 网络 | 无需联网（纯本地运行） | 如需共享数据则需局域网 |

### 2.2 服务端要求（可选）

当前版本为**纯前端版本**，无需服务端即可运行。如需多用户共享数据，需部署服务端（见第7节）。

| 项目 | 要求 |
|-----|------|
| Web 服务器 | Nginx / Apache / IIS / 任意静态文件服务器 |
| Node.js（开发） | v16+ |
| 磁盘空间 | ≥ 50MB |

### 2.3 不支持的环境

- ❌ IE 浏览器（不支持 ES6+ 语法）
- ❌ 移动端浏览器（界面未适配移动端）
- ❌ 禁用 JavaScript 的环境
- ❌ 隐私模式下 localStorage 被禁用的浏览器

## 3. 快速部署

### 3.1 单机使用（最简单）

```
1. 将整个项目文件夹复制到任意目录
2. 双击打开「TimMiniERP.html」
3. 使用默认账号登录：admin / 123456
```

### 3.2 局域网部署（多人访问，各自独立数据）

**方式一：使用 Nginx**

```nginx
server {
    listen 80;
    server_name erp.yourcompany.com;
    root /path/to/TimMiniERP;
    index TimMiniERP.html;

    location / {
        try_files $uri $uri/ /TimMiniERP.html;
    }
}
```

**方式二：使用 Node.js 简易服务器**

```bash
cd TimMiniERP
npx http-server -p 8080
# 访问 http://localhost:8080/TimMiniERP.html
```

**方式三：使用 Python**

```bash
cd TimMiniERP
python -m http.server 8080
```

### 3.3 重要说明

> ⚠️ **纯前端模式的局限性**：每个浏览器有独立的 localStorage，不同电脑/浏览器之间的数据**互不相通**。如需多人共享同一数据集，请连接 `server/` 目录下的 Node.js 后端数据库（见第7节），无需重新部署前端，登录后在「系统设置 → 系统信息」中填写后端地址即可。

## 5. 多账套管理

### 5.1 概念说明

**账套**是数据隔离的基本单位，适用于以下场景：

- 同一系统管理多个公司/分公司的数据
- 同一公司管理多个仓库（各仓库数据独立）
- 不同部门需要独立的数据空间
- 测试环境与正式环境隔离

系统内置一个 **id 为 `default` 的"演示账套"**，预置了完整的示例数据（商品、供应商、出入库记录等），供初次接触系统的用户体验各项功能；该账套不可删除，但可以重命名。**除演示账套外，新建的账套都是完全空白的**：只会创建一个可登录的管理员账号（`admin` / `123456`）和默认权限矩阵，不包含任何商品/供应商/客户/出入库等业务基础数据或单据，需要自行录入真实数据。

### 5.2 账套操作

#### 创建账套
1. 以管理员登录 → 系统设置 → 📂 账套管理
2. 点击「+ 新建账套」
3. 输入账套名称和描述
4. 新账套是空白账套，仅包含一个管理员账号，不含示例数据

#### 切换账套
- **方式一**：系统设置 → 账套管理 → 点击「🔄 切换到此账套」
- **方式二**：登录页选择目标账套后登录

> ⚠️ 切换账套后当前会话将结束，需要重新登录。切换到已经使用过的账套不会清空或重置该账套已有的数据。

#### 删除账套
- 内置的演示账套（id 为 `default`）不可删除
- 删除前系统会显示数据统计，建议先导出备份
- 删除后，使用该账套的用户不会被删除，但数据将丢失

#### 导出账套
- 点击账套卡片上的「📤」按钮
- 导出为 JSON 文件，包含该账套的所有数据

### 5.3 账套间数据关系

| 数据类型 | 是否跨账套共享 |
|---------|-------------|
| 系统名称/品牌 | ✅ 共享 |
| 打印设置 | ✅ 共享 |
| 主题设置 | ✅ 共享 |
| 用户数据 | ❌ 独立 |
| 商品数据 | ❌ 独立 |
| 出入库记录 | ❌ 独立 |
| 权限配置 | ❌ 独立 |
| 角色配置 | ❌ 独立 |

## 6. 多用户并发与负载分析

### 6.1 当前架构分析

当前纯前端版本的数据存储特性：

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  用户A浏览器  │  │  用户B浏览器  │  │  用户C浏览器  │
│  localStorage│  │  localStorage│  │  localStorage│
│  (独立数据)   │  │  (独立数据)   │  │  (独立数据)   │
└─────────────┘  └─────────────┘  └─────────────┘
      ↑                ↑                ↑
      └────────────────┼────────────────┘
                       │
              各自独立，互不影响
```

### 6.2 并发问题总结

| 场景 | 是否存在问题 | 说明 |
|-----|-----------|------|
| 多人同时操作同一浏览器 | ❌ 无问题 | 单线程，不存在并发 |
| 多人各自打开系统 | ⚠️ 数据独立 | 每人看到自己的数据，互不可见 |
| 同一人开多个标签页 | ✅ 正常 | localStorage 变更实时同步 |
| 多人需要共享数据 | ❌ 不支持 | 需升级服务端数据库版本 |

### 6.3 性能瓶颈

| 瓶颈类型 | 影响 | 解决方案 |
|---------|------|---------|
| localStorage 容量 | 单账套最多约 3 万条记录 | 定期清理/归档旧数据 |
| JSON 解析性能 | 数据量大时读写变慢 | 控制单集合数据量 < 5000 条 |
| 浏览器标签内存 | 约 100-300MB/标签 | 关闭不用的标签页 |
| 无并发控制 | 多标签同时写入可能冲突 | 避免多人同时操作同一数据 |

### 6.4 推荐部署方案

| 用户规模 | 推荐方案 | 说明 |
|---------|---------|------|
| 1-3 人 | 纯前端版本 | 每人独立使用，定期手动同步 |
| 3-10 人 | 前端 + 轻量后端 | 使用 Node.js/Python 提供 API |
| 10-50 人 | 前端 + 数据库服务器 | MySQL/PostgreSQL |
| 50+ 人 | 完整 C/S 或 B/S 架构 | 需重新设计为服务端渲染 |

## 7. 数据库配置与升级路径

### 7.1 两种运行模式

| | 纯本地模式（默认） | 服务端数据库模式（可选） |
|---|---|---|
| 存储位置 | 浏览器 localStorage | `server/data/wms.db`（SQLite 文件） |
| 是否需要部署 | 不需要，双击 HTML 即可 | 需要运行 `server/` 下的 Node.js 服务 |
| 多端共享数据 | ❌ 不支持 | ✅ 支持 |
| 容量上限 | 5-10MB（浏览器限制） | 受磁盘空间限制，无实质上限 |
| 并发写入 | 无意义（单浏览器） | 后台异步同步，最后写入者生效（见 7.5 局限说明） |
| 配置方式 | 无需配置 | 「系统设置 → 系统信息」填写后端地址并连接 |

两种模式使用同一套前端代码，`js/data.js` 中的 `DB` 对象是唯一数据入口：默认只操作 localStorage；连接服务端后，每次 `DB.set()` 写入都会在后台异步 `PUT` 到后端 API，同时保留本地写入，界面操作不受网络延迟影响。

### 7.2 服务端技术选型：Node.js + 可插拔数据库后端（SQLite 默认 / MySQL 可选）

`server/` 目录下的后端用 `DB_TYPE` 环境变量（`server/.env`）选择数据库实现，两种实现暴露完全一样的接口，`server.js` 的 API 路由不需要关心当前用的是哪个：

```
server/
├── server.js          # Express API 路由，统一 await db.xxx()，不关心具体后端
├── db.js              # 后端选择器：按 DB_TYPE 加载 db-sqlite.js 或 db-mysql.js
├── db-sqlite.js        # SQLite 实现（默认）
├── db-mysql.js         # MySQL 实现（可选，见 7.3）
├── package.json
├── .env.example        # 复制为 .env 后可自定义 DB_TYPE/端口/数据库连接等
└── data/wms.db          # DB_TYPE=sqlite 时，首次启动自动创建（已加入 .gitignore）
```

**默认方案：内置 `node:sqlite`**（`db-sqlite.js`）——用 Node.js **内置**的 `node:sqlite` 模块（Node 22.5+ 自带），而非社区常用的 `better-sqlite3`。原因是 `better-sqlite3` 需要 node-gyp 原生编译，在没有安装 Visual Studio C++ 构建工具的 Windows 机器上会安装失败；`node:sqlite` 是标准库的一部分，无需任何原生编译依赖，零配置开箱即用，适合个人/小团队快速部署。

**可选方案：独立 MySQL 数据库**（`db-mysql.js`）——通过 `mysql2` 连接你自己部署/托管的 MySQL 或 MariaDB，适合需要集中管理数据库、做定期备份策略、或已经有现成 MySQL 基础设施的场景。配置方法见 7.3。

两种实现共用同一套表结构（字段名、数据模型完全一致，只是 SQL 方言不同）：

```sql
-- 账套表
CREATE TABLE accounts (
  id TEXT PRIMARY KEY,           -- MySQL: VARCHAR(64) PRIMARY KEY
  name TEXT NOT NULL,            -- MySQL: VARCHAR(255) NOT NULL
  desc TEXT DEFAULT '',          -- MySQL: `desc` TEXT（desc 是保留字，需反引号）
  created_at TEXT NOT NULL       -- MySQL: VARCHAR(32) NOT NULL
);

-- 全局配置（预留，当前版本前端的系统名称/主题/打印设置仍存本地，未接入同步）
CREATE TABLE global_config (
  key TEXT PRIMARY KEY,          -- MySQL: `key` VARCHAR(191) PRIMARY KEY
  value TEXT NOT NULL,           -- MySQL: value LONGTEXT NOT NULL
  updated_at TEXT NOT NULL
);

-- 账套业务数据：每个账套的每个集合（goods/inbounds/...）整体存成一行 JSON，
-- 与前端 localStorage 里 "一个 key 对应一个数组" 的模型一一对应
CREATE TABLE collections (
  account_id TEXT NOT NULL,      -- MySQL: VARCHAR(64)
  collection TEXT NOT NULL,      -- MySQL: VARCHAR(191)
  data TEXT NOT NULL,            -- MySQL: LONGTEXT（商品图片等 base64 数据可能超过 TEXT 64KB 上限）
  updated_at TEXT NOT NULL,
  PRIMARY KEY (account_id, collection),
  FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE CASCADE
);
```

两个实现都会在服务启动时自动建表（`CREATE TABLE IF NOT EXISTS`），不需要手动执行建表脚本。

**API 路由**（`server.js`，与数据库后端无关，始终不变）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查，返回值里的 `dbType` 字段可确认当前连的是 sqlite 还是 mysql |
| GET/POST | `/api/accounts` | 账套列表 / 创建账套（可传入前端已生成的 id，保持前后端 id 一致） |
| PUT/DELETE | `/api/accounts/:id` | 重命名 / 删除账套 |
| GET/PUT | `/api/config/:key` | 全局配置读写（当前前端未接入） |
| GET/PUT | `/api/:accountId/_all` | 批量拉取 / 写入某账套下全部集合（登录/连接时一次性同步用） |
| GET/PUT | `/api/:accountId/:collection` | 单个集合读写（对应前端每次 `DB.set(key, val)`） |
| POST | `/api/admin/test-db-config` | 测试数据库连接（不落盘），配合前端"后端数据库类型配置"面板 |
| POST | `/api/admin/apply-db-config` | 保存数据库配置到 `.env` 并自动重启进程使其生效 |

### 7.3 部署步骤

```bash
# 1. 安装依赖（仅需一次；package.json 已包含 mysql2，即使用 SQLite 也会一起装上，无需额外操作）
cd server
npm install

# 2. 复制配置文件
cp .env.example .env
```

**方式一：SQLite（默认，跳过下面 MySQL 配置直接启动即可）**

编辑 `.env`，确认 `DB_TYPE=sqlite`（默认值），可按需修改 `DB_PATH`/`PORT`/`CORS_ORIGIN`，然后：

```bash
npm start
# 输出 "WMS API server listening on http://localhost:3000 (DB_TYPE=sqlite)" 即成功
```

**方式二：独立 MySQL 数据库**

#### 第 0 步：确认本机/目标服务器上有可连接的 MySQL

Windows 本机安装的 MySQL 通常以服务形式运行，用 PowerShell 检查：

```powershell
Get-Service | Where-Object { $_.Name -like '*mysql*' }
# Status 是 Running 就说明数据库已经在跑了，记下 Name（比如 MySQL80、MySQL84），
# 不是 Running 的话用 Start-Service <服务名> 启动
```

也可以直接看有没有监听 3306 端口：

```powershell
netstat -ano | findstr ":3306"
```

如果密码忘了：优先去找当初安装时记下的密码，或者用 MySQL Workbench / Navicat / DBeaver 之类图形工具里保存过的连接信息查看；账号密码这类敏感信息不建议贴到聊天记录里排查，本地一步步试是最稳妥的方式。实在找不回，就只能按 MySQL 官方文档的「重置 root 密码」流程（`--skip-grant-tables` 方式）来重置，这里不展开。

#### 更简单的方式：后台一键配置（推荐，不用手改 .env）

如果不想手动编辑 `.env` 文件，前端已连接后端的情况下，登录后进入「系统设置 → 系统信息」，
"后端数据库类型配置"卡片里可以直接：
1. 选择数据库类型为 MySQL，填写主机/端口/用户名/密码/数据库名
2. 点击"测试连接"，成功会显示 MySQL 版本号
3. 点击"保存并应用（自动重启）"——后端会自动把配置写入 `.env`（旧文件备份为 `.env.bak`）
   并自动重启进程使其生效，前端会轮询等待重启完成后自动刷新，全程不需要手动改文件、
   不需要手动重启命令。

这个能力对应的接口是 `POST /api/admin/test-db-config` 和 `POST /api/admin/apply-db-config`，
和其它接口一样没有做身份校验，跟当前项目"局域网内网自用"的整体安全模型一致；如果部署在
不受信任的网络环境里，请自行在前面加一层反向代理鉴权，或避免对外网暴露这两个接口。

#### 手动方式：第 1-4 步配置并启动

1. 准备好一个 MySQL 5.7+ / 8.0+ 或 MariaDB 实例（本机安装、局域网服务器、或云数据库均可），确认网络可达。
2. 编辑 `server/.env`：
   ```ini
   DB_TYPE=mysql
   MYSQL_HOST=localhost
   MYSQL_PORT=3306
   MYSQL_USER=root
   MYSQL_PASSWORD=你的密码
   MYSQL_DATABASE=wms_db
   ```
3. `MYSQL_USER` 账号需要有 `CREATE DATABASE` 权限——服务启动时会自动执行 `CREATE DATABASE IF NOT EXISTS wms_db CHARACTER SET utf8mb4` 并建好三张表。如果是云数据库/托管 MySQL、账号没有建库权限，请先手动执行一次：
   ```sql
   CREATE DATABASE wms_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   ```
   再启动服务，建表这一步（`CREATE TABLE IF NOT EXISTS`）普通账号权限通常就够用。
4. 启动：
   ```bash
   npm start
   ```
   看到下面这行说明数据库连接、建库建表全部成功（这是本项目在本机 MySQL 8.4.11 上实测通过的真实输出）：
   ```
   WMS API server listening on http://localhost:3000 (DB_TYPE=mysql)
   ```
   连接失败会在这里直接报错退出，不会启动一半假装成功。

#### 常见报错对照

| 报错 | 原因 | 处理方式 |
|---|---|---|
| `ER_ACCESS_DENIED_ERROR` | 账号或密码错误 | 检查 `MYSQL_USER`/`MYSQL_PASSWORD`，确认是这台 MySQL 实际的账号密码，不是随便猜的默认值 |
| `ECONNREFUSED` | 目标地址/端口没有服务在监听 | 确认 MySQL 服务是否已启动（见第0步）、`MYSQL_HOST`/`MYSQL_PORT` 是否填对 |
| `ETIMEDOUT` | 网络不通（常见于远程/云数据库） | 检查防火墙、安全组、是否需要先给当前 IP 加白名单 |
| `ER_DBACCESS_DENIED_ERROR` | 账号没有建库权限 | 按上面第3步手动建库，或联系 DBA 提权 |

#### 验证连接是否真的通了

启动后除了看控制台输出，还可以直接访问健康检查接口，返回里的 `dbType` 字段能确认当前连的是哪个数据库：

```bash
curl http://localhost:3000/api/health
# {"ok":true,"time":"...","dbType":"mysql"}
```

> ⚠️ 从 SQLite 切到 MySQL（或反过来）不会自动迁移数据——两边是两份独立的数据库文件/实例。如果已经用 SQLite 积累了数据，想切到 MySQL，请先在前端「系统设置 → 数据管理」导出账套数据备份，切换 `DB_TYPE` 重启服务后，用同一份备份重新导入，或者直接让前端走一次正常的"首次连接"流程（见 7.4）把本地 localStorage 数据推送到新的 MySQL 库。

局域网内其他电脑要访问，需将 `.env` 中 `PORT` 对应的端口在防火墙放行，前端「系统设置 → 系统信息」里填写 `http://<部署该服务的电脑IP>:3000` 即可连接。生产环境建议用 `pm2`/`systemd`/Windows 服务等方式让 `node server.js` 保持常驻运行，并在前面套一层 Nginx 反向代理 + HTTPS。

### 7.4 首次连接时的数据合并规则

登录后在「系统设置 → 系统信息」填写后端地址并点击"连接并同步"时：

1. 探测后端 `/api/health`，2.5 秒超时，探测失败则维持本地模式不受影响。
2. 若服务端对应账套下**完全没有数据**（全新后端）：把本地当前数据整体推送上去，作为服务端的初始数据。
3. 若服务端**已有数据**（其他终端已经连接并同步过）：以服务端数据为准，覆盖本地 localStorage 中的对应集合。

也就是说，第一台连接的电脑负责"播种"服务端数据库，后续电脑连接后会拉取到同一份数据。之后每次本地写入（新建/编辑/删除/审核等）都会在后台异步同步到服务端，无需手动操作。

### 7.5 已知局限

- **无冲突解决机制**：两台电脑几乎同时修改同一条记录时，以后写入服务端的一方为准，不会弹出冲突提示，适合小团队错峰操作，不适合真正的多人实时协同编辑。
- **网络中断后不会自动重连**：写入失败会静默降级为本地模式，需要在「系统设置 → 系统信息」重新点击"连接并同步"，或刷新页面重新触发探测。
- **系统名称/主题/打印设置等全局配置不参与同步**，仍然是各浏览器本地独立配置。
- **MySQL 后端未内置连接池监控/自动重连告警**：`mysql2` 连接池本身会在网络抖动后自动重连，但如果 MySQL 服务长时间不可用，API 请求会持续报 500，需要人工介入排查，没有额外的健康检查/告警机制。
- 若未来需要支持数十人以上并发、真正的事务级一致性或实时协同，可以在现有 MySQL 方案基础上引入连接池调优、读写分离或 WebSocket 广播变更，但这属于更大规模的架构升级，超出当前版本范围。

### 11.1 纯前端版本安全须知

| 风险 | 说明 | 缓解措施 |
|-----|------|---------|
| 数据明文存储 | localStorage 数据未加密 | 不要存储敏感信息 |

4. **HTTPS**：局域网部署时也建议使用 HTTPS
5. **审计日志**：定期检查审计日志，发现异常操作

## 12. 常见问题

### Q1: 数据突然消失？
**A**: 可能是浏览器清除了缓存。检查是否使用了隐私模式或清理工具。建议开启自动备份。

### Q2: 多人使用数据不同步？
**A**: 纯本地模式下每个浏览器数据独立。如需共享数据，启动 `server/` 下的后端并在「系统设置 → 系统信息」连接即可，无需重新部署前端（见第7节）。

### Q3: localStorage 满了怎么办？
**A**: 
1. 清理旧数据（归档已完成的单据）
2. 删除不需要的账套
3. 连接服务端数据库模式（数据存 SQLite 文件，不再受浏览器 5-10MB 限制）

### Q4: 如何迁移到新电脑？
**A**: 未连接服务端时，在旧电脑上执行「完整备份」，将备份文件拷贝到新电脑，在新电脑上执行「数据恢复」。已连接服务端时，新电脑直接连接同一后端地址即可自动拉取数据，无需手动备份迁移。

### Q5: 如何从纯本地模式切换到服务端数据库模式？
**A**: 
1. 参照第 7.3 节启动 `server/` 下的 Node.js 后端
2. 登录系统后进入「系统设置 → 系统信息」，填写后端地址并点击"连接并同步"
3. 首次连接会自动把本地数据整体推送到服务端（见 7.4 节合并规则），无需手写迁移脚本
4. 其他电脑连接同一后端地址即可看到同一份数据

### Q6: 打印时 Logo 显示异常？
**A**: 
1. 项目默认使用内置的 `LOGO.svg` 品牌图标；如需换成自己的图片，把文件放到项目根目录后在「打印设置」的 Logo 路径中填对应文件名即可
2. 找不到图片时会自动隐藏 Logo 区域，不影响单据其他内容打印
3. 也可以在打印设置中直接取消勾选「显示 Logo」
